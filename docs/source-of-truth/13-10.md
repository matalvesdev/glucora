13.10 — Local Development & Environment Blueprint


Status: Implementation Source of Truth


1. Objetivo
Garantir que qualquer engenheiro/agente consiga reproduzir o ambiente local sem depender de configuração tribal ou serviços cloud ainda não escolhidos.


2. Requisitos locais
Node.js LTS compatível com stack aprovada; pnpm; Docker/Compose; PostgreSQL container; web/API executáveis localmente; migrations/seed; scripts de lint/typecheck/test/build.


3. Ambiente
`.env.example` documenta variáveis, tipo, finalidade e se obrigatória. `.env.local`/secrets permanecem fora do Git. Config validation falha cedo quando valor obrigatório ausente/inválido.


4. Docker Compose inicial
PostgreSQL obrigatório. Adicionar mail catcher/object storage/queue emulator somente quando capability exigir. Não iniciar dezenas de serviços por antecipação.


5. Database
Script `db:up`, `db:migrate`, `db:reset`, `db:seed`, `db:test` ou equivalentes. Seed usa dados sintéticos e cenários úteis, nunca dados reais de pacientes.


6. Developer commands
`dev`, `dev:web`, `dev:api`, `build`, `lint`, `typecheck`, `test`, `test:integration`, `test:e2e`, `db:migrate`, `openapi:check`, `ai:eval` quando implementado.


7. Ports/names
Definir defaults estáveis e configuráveis; health endpoints acessíveis. Evitar dependência em localhost hardcoded dentro do domínio.


8. Local auth
Até Identity Provider ADR, usar adapter/dev strategy explicitamente não-produção que preserve interfaces reais e authorization semantics. Não criar backdoor que possa ser habilitado em produção.


9. Local AI
Model provider real pode ser opcional; fornecer deterministic/fake adapter para testes e desenvolvimento de fluxos. Evals reais executam em ambiente controlado quando provider selecionado.


10. Time & locale
Tests devem poder fixar clock/timezone. Armazenamento em UTC; apresentação considera timezone/locale. Não depender do timezone da máquina do developer.


11. Observability local
Structured logs legíveis; correlation IDs; opção de pretty-print somente dev. Não exigir SaaS externo para executar localmente.


12. Setup target
Clone → install → env copy → docker up → migrate/seed → dev. O caminho deve ser automatizado/documentado e verificável em CI quando possível.


13. Regra final
O ambiente local deve refletir contratos reais da arquitetura sem exigir infraestrutura de produção para desenvolver o MVP.
