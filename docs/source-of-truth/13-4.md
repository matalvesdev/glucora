13.4 — API & Contract Blueprint


Status: Implementation Source of Truth


1. Objetivo
Definir a API HTTP inicial e os contratos entre web, backend e futuras integrações, preservando versionamento, idempotência, autorização e observabilidade.


2. Estilo
REST/JSON para MVP, OpenAPI como contrato oficial e JSON Schema/type generation quando útil. Não adotar GraphQL sem necessidade comprovada.


3. Prefixo
`/v1` para API pública/consumer-facing. Endpoints internos podem ser separados por namespace, mas não devem depender de rotas privadas obscuras para garantir segurança.


4. Recursos iniciais
/auth ou integração com provider selecionado; /me; /consents; /profile; /observations; /medications; /context-events; /timeline; /insights; /consultations/reports; /shares; /integrations; /exports; /privacy-requests; /feedback.


5. Convenções
IDs opacos; timestamps ISO-8601 UTC; units explícitas; locale/timezone como contexto; pagination cursor-based quando coleção puder crescer; filtering limitado e documentado.


6. Errors
Envelope consistente com code, message segura ao usuário, request_id e field errors quando aplicável. Nunca expor stack trace, SQL ou dado sensível.


7. Idempotência
POSTs com efeito duplicável relevante suportam `Idempotency-Key` ou mecanismo equivalente: imports, share creation, privacy requests, payment future, integration callbacks e jobs críticos. Persistir key + scoped actor + request hash + response/result conforme necessidade.


8. Concurrency
Usar version/ETag/updated_at checks para updates em estados sensíveis quando lost update for relevante.


9. Authorization
Autenticação não equivale a autorização. Cada route/application command avalia actor, subject, organization context, consent/purpose e resource ownership.


10. Validation
Input validado na borda; domínio revalida invariantes. Não confiar em tipos TypeScript como validação runtime.


11. Audit
Mudanças de consentimento, sharing, privileged actions, data correction/deletion e admin actions geram audit apropriado.


12. API de IA
Não expor endpoint genérico `/chat` irrestrito como núcleo. Expor capabilities/intents específicas: summarize timeline, prepare consultation, explain approved content, generate low-risk contextual observation, com risk classification e output schema.


13. Integration webhooks
Assinatura/verificação, replay protection, dedupe, rate limiting, raw-event preservation quando necessário e processamento assíncrono.


14. OpenAPI CI
Mudança breaking exige versão/compatibility review. Contract tests fazem parte do pipeline.


15. Regra final
A API representa capabilities governadas do produto; não é um CRUD irrestrito sobre tabelas do banco.
