13.5 — Security, Privacy & Authorization Blueprint


Status: Implementation Source of Truth


1. Objetivo
Traduzir Security Architecture, LGPD/Compliance e Consent em controles implementáveis desde o primeiro commit.


2. Trust boundaries
Browser/PWA; edge; API; database/storage; async jobs; third-party integrations; AI providers; admin/support. Toda travessia de boundary deve possuir autenticação/validação/autorização adequada.


3. Identity
Identity provider permanece ADR aberto. Aplicação deve usar abstraction/adapters para session/user identity sem acoplar domínio ao fornecedor.


4. Authorization model
RBAC simples para organizational roles combinado com ownership + consent/purpose-based checks. Roles não concedem acesso automático a health data. Policies ficam server-side.


5. Roles iniciais
Consumer user; organization admin; professional/care-team member quando Pro existir; support operator; internal privileged admin. MVP Consumer deve começar com superfície mínima.


6. Consent enforcement
Consent é estado executável. Cada processing capability relevante declara purpose(s) e verifica grant/legal context antes do uso. Revocation deve afetar novas operações rapidamente.


7. Data minimization
API, logs, analytics, error tracking e AI context recebem apenas dados necessários. Nunca inserir health payload em URL/querystring/UTM/ad pixels.


8. Encryption
TLS em trânsito; encryption at rest via infraestrutura selecionada; sensitive secrets em secrets manager/KMS quando cloud definido. Não criar criptografia customizada.


9. Secrets
`.env` somente local; `.env.example` sem valores. CI/prod usam secret store. Secret scanning habilitado.


10. Sessions/tokens
HttpOnly/Secure/SameSite cookies preferidos quando arquitetura web permitir; tokens com curta validade/rotation conforme provider. CSRF strategy compatível com auth model.


11. Abuse controls
Rate limits, brute-force protection, request size limits, schema validation, safe file upload rules quando existir, SSRF/injection protections e dependency hygiene.


12. Audit
Separar application logs de audit events. Consent/share/privacy/admin/security events devem ser reconstruíveis sem registrar dado clínico bruto desnecessário.


13. Support access
Sem acesso irrestrito por padrão. Privileged/break-glass deve ser raro, justificado e auditado.


14. Privacy rights implementation
Endpoints/workflows para export, correction, deletion, consent history/revocation e contestation. Async workflow deve manter status e evidence of completion.


15. Security testing
Authorization matrix tests são obrigatórios. OWASP ASVS/API Security Top 10 como referência prática; threat model para sharing, integrations, AI tools e admin surfaces.


16. Regra final
Acesso deve ser negado por padrão e concedido pela combinação correta de identidade, autoridade, finalidade e contexto — nunca apenas porque o request veio de usuário autenticado.
