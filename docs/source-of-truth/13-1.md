13.1 — Repository & Monorepo Blueprint


Status: Implementation Source of Truth


1. Objetivo
Definir a estrutura inicial do repositório que materializa as decisões aprovadas sem introduzir complexidade distribuída prematura.

3. Package manager
Preferência: pnpm workspaces pela eficiência e suporte a monorepo. Caso o ambiente alvo exija outro gerenciador, criar ADR antes da mudança.


4. Apps e services
`apps/web`: React + TypeScript + Vite + Tailwind + shadcn/ui.
`services/api`: Node.js + TypeScript + Fastify.


5. Packages
`contracts`: OpenAPI/JSON Schema/types compartilhados; `domain`: tipos/objetos de domínio sem dependência de framework; `ui`: design system; `config`: lint/tsconfig/env; `observability`: logging/tracing abstractions; `test-utils`: factories/fixtures seguras.


6. Regras de dependência
Web não importa infraestrutura do API. Domain não depende de Fastify/React/PostgreSQL. Contracts não dependem de implementações. Infrastructure depende de interfaces, não o contrário.


7. Organização do backend
Modular monolith por domínio, não por camada global. Cada módulo contém domain/application/adapters/interfaces quando necessário.


8. Branching
Main protegida; mudanças relevantes via PR. Feature branches curtas. Evitar long-lived develop branch salvo necessidade comprovada.


9. Commits
Conventional Commits recomendado. Mudanças de arquitetura/clinical/compliance devem referenciar ADR/decision quando aplicável.


10. Não incluir inicialmente
Microservices, Kafka, Kubernetes, service mesh, graph DB, vector DB dedicada, data lake, CQRS/event sourcing completo ou multi-region sem ADR e requirement.


11. Regra final
A estrutura deve facilitar evolução sem transformar possibilidades futuras em dependências atuais.
