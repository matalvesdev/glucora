13.2 — Domain Modules & Boundaries


Status: Implementation Source of Truth


1. Objetivo
Converter o Domain Model da Glucora em módulos implementáveis com ownership claro e baixo acoplamento.


2. Módulos iniciais
Identity — usuário, sessão, credenciais/federação e account status.
Consent — consent grants, purposes, versions, revocation e authorization consequences.
Health Profile — informações declaradas relevantes ao contexto longitudinal.
Measurements — observações/medições registradas manualmente ou importadas.
Medication & Therapy Context — registro contextual de medicamentos/terapia sem autoridade para prescrição.
Lifestyle Context — alimentação, atividade, sono, sintomas e eventos contextuais aprovados.
Longitudinal Record — agregação canônica e relações temporais/provenance.
Timeline — projeção para experiência temporal; não canônica.
Insights — descriptive patterns e contextual hypotheses dentro dos limites clínicos.
Consultation — preparation packs, summaries, questions e reports.
Sharing — grants, recipients, artifacts, revocation e audit.
Integrations — connectors, imports, normalization, sync state e provenance.
AI Orchestration — intent/risk, context building, retrieval, model gateway, validation e traces permitidos.
Audit — security/privacy/domain audit events.
Notifications — preferências e mensagens permitidas; sem lógica clínica autônoma.


3. Regras
Cada módulo possui API interna explícita. Nenhum módulo lê tabelas internas de outro diretamente salvo exceção documentada. Comunicação síncrona via application interfaces; assíncrona via jobs/domain events somente quando benefício real.


4. Domain objects
Entidades devem representar fatos e estados do domínio, não espelhar diretamente JSON de fornecedores. Dados externos passam por adapters/normalization.


5. Fact taxonomy
Preservar FACT, DECLARATION, DERIVATION, INFERENCE e CLINICAL_ASSERTION. Nunca persistir inference como measurement original.


6. Temporal model
Separar occurred_at, recorded_at, ingested_at, effective_from/to e superseded_at quando aplicável.


7. Correções
Correção cria versão/supersession/qualificação; não reescreve silenciosamente histórico relevante.


8. Authorization
Consent, user/organization role e data purpose são avaliados antes do acesso ao módulo/dado. Organização/payer não ganha acesso individual por propriedade da conta.


9. Extração futura
Microservice só é candidato quando boundary, escala, ownership, deployment isolation ou failure isolation justificarem custo distribuído.


10. Regra final
Bounded context é fronteira semântica e de responsabilidade, não desculpa para multiplicar serviços.
