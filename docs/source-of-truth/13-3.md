13.3 — Data Schema & Persistence Blueprint


Status: Implementation Source of Truth


1. Objetivo
Definir o schema lógico inicial para PostgreSQL preservando provenance, temporalidade, consentimento, correção e separação entre dados canônicos e projeções.


2. Schemas lógicos sugeridos
`identity`, `consent`, `health`, `integration`, `sharing`, `ai`, `audit` ou namespaces equivalentes via convenção de tabelas. A escolha de múltiplos PostgreSQL schemas físicos pode ser simplificada inicialmente se migrations/tooling ficarem mais claros.


3. Entidades iniciais
users; user_profiles; organizations; organization_memberships; consent_purposes; consent_grants; consent_events; health_profiles; observations; observation_versions; medications; therapy_context_events; meals_or_nutrition_events; activity_events; sleep_events; symptom_events; notes/context_events; source_connections; import_runs; source_records; provenance_records; timeline_projection; insight_records; insight_evidence_links; consultation_reports; share_grants; shared_artifacts; audit_events; ai_runs; ai_retrieval_refs; user_feedback.


4. Identificadores
UUID/UUIDv7 ou alternativa aprovada. Não expor sequência interna previsível quando não necessário. Estratégia final de UUID library pertence à implementação, não exige novo ADR salvo impacto sistêmico.


5. Observation core
Campos mínimos: id, user_id, type/code, value/structured_payload, unit quando aplicável, occurred_at, recorded_at, ingested_at, source_type, source_id, provenance_id, fact_class, status, version, created_at.


6. Provenance
Todo dado importado/derivado relevante deve conseguir apontar para origem, connector/source record, transformação/version e timestamp. AI output aponta para inputs/evidence/model bundle sem armazenar conteúdo sensível desnecessário.


7. Correção e supersession
Não fazer hard update de histórico clinicamente relevante como default. Usar current/superseded relation ou history table conforme domínio.


8. Consent
Consent events são append-oriented e reconstruíveis: granted, denied, revoked, expired/version-reconsent quando aplicável. Current grant pode ser projeção/materialized state.


9. Projections
Timeline/search/report/analytics/vector embeddings são derivados. Podem ser deletados/reconstruídos sem alterar canonical record.


10. Soft delete vs deletion rights
Soft delete não substitui eliminação requerida. Implementar deletion workflow que trate canonical data, projections, vendor copies e backup lifecycle conforme `05.12`/Compliance.


11. Indexação
Começar com índices guiados por queries reais: user_id + occurred_at; consent current state; source dedupe keys; audit actor/time; jobs/status. Não adicionar extensões/time-series prematuramente.


12. Migrations
Versionadas no repositório, forward-safe, testadas, sem auto-sync destrutivo em produção.


13. ORM/query layer
Não congelado neste documento. Seleção de ORM/query builder pode ser decisão de implementação se não alterar arquitetura; preferir schema/migrations explícitas e type safety.


14. Regra final
PostgreSQL guarda fatos e estados confiáveis; interfaces de visualização, busca e IA não se tornam a fonte da verdade por conveniência.
